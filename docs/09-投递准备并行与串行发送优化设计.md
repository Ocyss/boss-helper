# 投递准备并行与串行发送优化设计

> 状态：MVP 已编码，等待人工验证<br>
> 更新日期：2026-08-12

## 目标与边界

将“逐条读取、筛选、生成、投递”的全串行流程拆成准备和提交两阶段。每页最多建立 10 个岗位的有界准备窗口，提前完成可安全并行的筛选与话术生成；实际 BOSS 请求和投递继续串行，并保留现有等待时间。该方案不等于批量突发请求，也不允许跨页预取。

## 已处理的原有约束

- `onJobCardClick()` 仍通过共享 `_jobDetail` 获取 JD，因此由并发为 1 的详情信号量保护。
- AI 招呼语已经拆成无站内副作用的 `prepare` 生成和投递成功后的 `commit` 发送。
- `deliveryLimit` 已在批次准备前和单项发送前硬检查；`RateLimitError`、`LimitError` 会终止本轮并清空待投递队列。
- 同公司、同 HR 去重改用真实公司/HR 标识，并在 `friend/add` 成功后写入。

## 推荐流水线

```text
本页取最多 10 个岗位
  -> 本地预过滤
  -> BOSS 详情池（并发 1）
  -> 详情过滤与地图判断
  -> AI 池（总并发 2）：AI 筛选 -> 纯生成招呼语
  -> 按原岗位顺序进入 ready 队列
  -> 串行复验 -> friend/add -> 读取 Boss 信息 -> WS 发送招呼语
  -> 等待既有 delayDeliveryInterval
```

MVP 常量：`PREPARE_BATCH_SIZE = 10`、`BOSS_DETAIL_CONCURRENCY = 1`、`AI_CONCURRENCY = 2`、`DELIVERY_CONCURRENCY = 1`、`PREPARED_TTL_MS = 10 * 60_000`。

## 队列状态与失效

单项状态为 `queued -> prefiltering -> detail -> ai_filtering -> greeting -> ready -> delivering -> delivered`，另有 `filtered`、`failed`、`stale`、`cancelled`、`partial`。每项保存 `runId`、岗位标识快照、原始顺序、配置指纹、生成话术、过期时间和重试次数。

超过 10 分钟、配置发生变化、岗位安全参数变化、已沟通、达到投递上限、页面切换或任务暂停时，准备结果必须作废。暂停使用 `AbortController + runId` 取消队列，无法中止的迟到 AI 结果直接丢弃。

执行器使用单实例锁阻止重复点击启动两轮任务，并以提交互斥保证公开单岗位执行和整页执行共用同一个串行投递通道。支持 Web Locks 的浏览器还会按 BOSS 账号获取跨标签页排他锁；若锁已被其他标签持有，本标签不会开始投递。浏览器不支持 Web Locks 时会明确记录降级日志，仅保留当前实例互斥，不使用不可靠的本地存储伪锁。配置或页面变化会终止整轮并要求重新开始，不会继续自动翻页。配置指纹只保存哈希，不持久化 Prompt、知识正文或模型密钥。

## 风控与异常

发送前硬性检查日限额；`RateLimitError` 或 `LimitError` 触发全局熔断，取消准备并清空待投递队列。准备完成不能缩短相邻实际投递间隔。

AI 超时或 429 最多重试 2 次并使用指数退避和抖动；JD 读取最多重试 1 次。`friend/add` 遇到传输中断、取消或 JSON 解析异常时结果不明确，必须立即停止且不得自动重试，提示用户先检查会话列表。唯一保留的二次请求是平台明确返回 120 人限制后，完成确认请求再携带 `cid=1` 重试一次；确认请求或该次重试结果不明确时同样停止。若 `friend/add` 已成功但读取 Boss 信息或 WS 发送失败，记录为 `partial`，禁止再次调用 `friend/add`。

`friend/add` 成功后立即更新本地已沟通状态，并紧邻写入同公司/同 HR 去重缓存。HTTP 成功返回与本地状态落盘之间无法组成跨网络事务，仍保留一个极短的不可消除窗口；人工验证需要覆盖在该阶段断网或关闭页面的恢复行为。

## 验收标准

- 任意时刻 BOSS 详情请求不超过 1、AI 请求不超过 2、同一账号跨标签页投递请求不超过 1、队列不超过 10。
- 暂停、换页、达到上限或命中频控后，不再产生新的投递请求。
- 相邻实际投递间隔不低于用户配置值，准备顺序不改变投递顺序。
- 任务结束后释放已完成项和模型中间状态，避免内存随岗位数持续增长。
